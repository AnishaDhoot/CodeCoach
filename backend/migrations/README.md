# Database migrations (Alembic)

Alembic owns the **Postgres** (hosted) schema. Local dev and the test suite use
SQLite via `Base.metadata.create_all`, so you normally don't run Alembic locally.

Config: [`alembic.ini`](../../alembic.ini) · env: [`env.py`](env.py). The DB URL is
taken from the app's `DATABASE_URL` at runtime (see `backend/database.py`), so the
same env var drives the app and the migrations.

## Deploy (hosted Postgres)

```bash
export DATABASE_URL="postgresql://…"   # provider gives postgres://…, normalized automatically
alembic upgrade head
```

Run this as a release/pre-deploy step **before** the new app version serves traffic.

## Common commands

```bash
alembic upgrade head                      # apply all pending migrations
alembic downgrade -1                       # roll back one
alembic current                            # show applied revision
alembic check                              # fail if models drift from migrations (use in CI)
alembic revision --autogenerate -m "msg"   # create a migration from model changes
```

## Notes

- Constraints are named via a convention in `backend/database.py` (`NAMING_CONVENTION`).
  This is required for SQLite batch ALTERs and keeps Postgres constraint names stable —
  **do not** remove it, and regenerate migrations if you change it.
- `env.py` enables `render_as_batch` only on SQLite, so autogenerated ALTERs work there too.
- Migration history: `0001 initial multi-tenant schema` (all tables incl. `users`,
  `user_problems`, and the nullable `user_id` columns from the Phase-2 expand step).
